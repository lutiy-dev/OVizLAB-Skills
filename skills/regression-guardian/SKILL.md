# Regression Guardian · Scoped QA Extension (LAB)

## Trigger
Use for Android phone/TV, authentication, frontend navigation, API/CLI/worker behavior, or any change with a working baseline to protect. For a pure new-feature verification without baseline, mark checks as functional acceptance, not regression PASS.

## Inputs
Exact baseline version and commit, confirmed scenarios and evidence, target candidate SHA, approved delta, affected surfaces (browser / functional API-CLI-job-worker / native device / mixed), device/browser matrix, existing test commands, permitted environment/data/credentials, rollback and report destination.

## Procedure
1. **Baseline first.** Build the expected-behavior matrix from source evidence; record known failures separately. Unverified baseline is NOT CONFIRMED and cannot prove a new regression.
2. **Select surfaces and depth before executing.** Map changed modules and adjacent callers to relevant browser pages, functional contracts or Android/device scenarios. Choose QUICK (one happy path plus highest-risk edge), SCOPED (all affected contracts), or REGRESSION (replay recorded baseline failures and changed adjacent behavior). Do not start a web browser for an API/CLI-only task, or demand a URL where no web UI exists. Avoid redundant exhaustive sweeps after adequate focused evidence.
3. **Isolation/permission preflight.** Confirm target repository, running revision, exact URL/service identity and downstream data stores before probing. Localhost may proxy production; never assume safe isolation from hostname. Prefer synthetic data, test identities and owned fixtures. READ-ONLY by default; any state-changing clicks, API writes, job starts, resets or fixtures require authorized target and reversible state. No unattended production mutations, credentials in chat or unapproved installations.
4. **Functional contract map.** For each affected API/CLI/job/worker flow record source contract, setup, input, expected outcome, exact response/exit code and actual durable state. Test successful execution plus relevant invalid input, auth/ownership, state transitions, cancellation/timeout, retries/idempotency, concurrency and partial-failure recovery where justified by scope. HTTP 2xx, enqueued jobs and launched commands are not proof of final effect. Preserve stdout/stderr separately; compare final state rather than a success toast alone.
5. **Browser QA only when relevant and available.** Exercise changed page and adjacent route on agreed desktop/mobile viewports. Capture actual screenshots or visual observations, URL, interactive tree/state, console/page errors and meaningful network failures where supported. Check key interactions, keyboard focus, scroll/overflow, loading/empty/error, accessibility, responsive layout and navigation. Use an existing supported browser; do not install browser tooling merely to achieve a nominal PASS. Browser access absent means BROWSER NOT TESTED, not UI PASS.
6. **Reproduce → repair handoff → replay.** A real defect needs precise original actions, initial state, evidence and expected behavior. If approved repairs are performed elsewhere, rerun original failing interaction and one adjacent happy path at the new SHA; compare before/after, categorize FIXED / STILL FAILING / NEW / NOT TESTED. Do not silently fix or expand the authorized scope during a QA run.
7. **Device-specific scenarios.** On Android TV/Phone keep D-pad focus, OK/Back, voice search, touch interaction, keyboard, landscape, playback, update and sign-in paths distinct when affected. Emulator/build PASS does not establish physical TV/Phone interaction PASS. For Archviz tools verify unchanged geometry IDs, render/workflow semantics and saved artifacts when touched; a pleasing preview is not source integrity proof.
8. **Evidence and reporting.** For each scenario state baseline, candidate, exact tested SHA/environment, performed command or UI sequence, expected/observed outcome, log/screenshot/artifact refs, PASS/FAIL/BLOCKED/NOT TESTED and severity. Separate browser, functional, device and integration coverage. Retain sanitized evidence and an authorized rollback plan; report cleanup of owned test data and any leftovers. Escalate critical changes to `pr-ci-verifier` but do not automatically merge, deploy or rewrite settings.

## Test Quality Review Gate (LAB v0.1)
Apply this **read-only review gate** when a PR adds/changes automated tests or when test results are used as evidence for regression approval. This assesses test credibility; it does not replace actual runtime replay or introduce a new Skill.

1. **Choose scope.** In INCREMENTAL mode review only test files changed by the target PR plus the fixtures/contracts they depend on; in FULL mode review a bounded, explicitly named test area. Use repository-native diff/search tools already available. Do not execute upstream scripts or install tools solely for review. If no test files are in scope, report NO IN-SCOPE TESTS, not PASS.
2. **Load local standards first.** Prefer the target repository's own AGENTS.md, test conventions, CI workflow and working fixture utilities. Record the precise rule/source for each finding. Do not transplant framework-specific rules (pytest markers, DataHub URNs, GraphQL helpers, etc.) into other projects.
3. **Check meaningful behavior.** Assertions should establish a user-visible or contract-relevant outcome and actual durable state, not only status 2xx, a non-null response, a screenshot's existence or a mocked implementation detail. Include one high-risk failure/edge path when justified; avoid brittle exact error-string checks, exhaustive combinations and tests of framework internals.
4. **Check isolation and cleanup.** Inspect shared mutable state, unique test data/names, fixture ownership and teardown (including failure paths), concurrency/inter-test dependencies, retries and bounded waits. No unapproved writes or cleanup against production or unidentified services. Prefer owned synthetic fixtures and existing project helpers. For Archviz, assert stable geometry IDs, dimensions and original workflow/JSON semantics when touched.
5. **Check environment/security.** Flag hardcoded live endpoints, credentials, customer identifiers, unsafe global mutations, test-only permission changes and CI bypasses. Preserve approved hooks and test configuration; a proposed test fix never authorizes a security override.
6. **Report deterministically.** Provide file:line evidence, local rule/source, expected vs observed risk and severity (BLOCKER = credible unsafe/unreliable evidence; WARNING = material quality concern; SUGGESTION = optional improvement). Record which checks actually ran and exact revision. Verdict: APPROVED only with no blockers or material unresolved warnings; NEEDS CHANGES for fixable issues; BLOCKED for missing decisive evidence or unsafe test setup; NOT TESTED where runtime execution is absent. A review verdict is not REGRESSION PASS.
7. **Handoff.** Send required test fixes to `safe-implementer` under a separately approved write scope; after implementation, repeat the targeted review and execute the affected checks via this Skill and `pr-ci-verifier` when relevant. No auto-fix, auto-merge or deployment.

## Observable UI Interaction Gate (LAB v0.1)
For an approved UI-affecting Android TV/Phone or browser scenario, when a supported device/browser automation surface **actually exists**:
1. **Observe BEFORE action:** record device/session identifier, app/build revision, current screen, screenshot and accessibility/UI hierarchy (or DOM/interactive tree), focused element and visible loading state. Establish the expected target from hierarchy semantics; never infer a safe tap coordinate solely from an image. For D-pad flows, identify the currently focused control before pressing OK/Back.
2. **ACT once within approved test fixtures:** perform the smallest scoped tap, key, text entry or navigation event; capture the exact action and timestamp/step label. Never invent or assume an Xcode `DeviceEventSynthesize` tool in Android/Codex. ADB, UiAutomator, browser driver or MCP may be used only if installed, authorized and actually verified for this target. No production accounts or irreversible clicks.
3. **Observe AFTER action:** capture fresh hierarchy/focus/screenshot, relevant logs and actual final state. Compare observed result to the documented expectation, not merely the animation or successful event dispatch. If busy/loading/transient, inspect again after a bounded observation; retry the interaction at most once **after** inspecting a new hierarchy and only when safe and idempotent. Do not conceal persistent failures behind repeated retries.
4. **Classify outcome:** FUNCTIONAL FAIL (wrong navigation, missing expected state, unresponsive button, crash), VISUAL FAIL (clipped/overlapping/out-of-screen content), TRANSIENT (verified eventual completion), EXPECTED EMPTY/PERMISSION STATE, PASS or BLOCKED/NOT TESTED. Include before/after evidence paths and target device type; a successful build is not an interaction PASS.
5. **Close owned sessions:** preserve sanitized evidence, terminate only test sessions/processes owned by this run, disclose leaks/leftovers. A physical-device PASS and an emulator PASS are separate claims. Skip this gate for non-UI tests.

## Acceptance / PASS-FAIL
- **GENERATED:** test plan or scenario matrix exists, not a completed run.
- **VALIDATED:** deterministic static/unit/build checks actually ran on recorded SHA.
- **TESTED:** real browser, functional endpoint, process or device execution observed for a named scenario with final outcome evidence.
- **REGRESSION PASS:** verified prior baseline, required scenarios replayed and no new confirmed failure; other untested surfaces remain NOT TESTED.
- **FAIL:** verified unexpected behavior relative to the approved contract/baseline. A pre-existing failure is not a newly introduced regression without evidence.
- **BLOCKED / NOT CONFIRMED:** unsafe or unidentified environment, missing test access, ambiguous baseline, incomplete result, absent screenshots/device, or unavailable required checks.

## STOP
Stop unsafe probes, production writes, unapproved data/session clearing, destructive reset, hidden credentials, unauthorized test-tool installation, critical regression or missing safe rollback. READ-ONLY research may continue; do not claim full QA when only build/tests were inspected.
